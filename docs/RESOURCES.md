# 資源消耗評估與原因分析

**繁體中文** | [English](RESOURCES.en.md)

適用來源：DragonCities Glass UI 1.0.2。評估日期：2026-11-03。

## 結論

**主機的大宗額外負載集中在安裝建置；玻璃效果的即時運算在訪客瀏覽器。** 日常主機仍需處理原面板的 PHP、API、WebSocket 配套與靜態檔案流量，不能把「前端主題」理解成完全沒有主機成本。

| 階段 | 主要消耗 | 評估 |
| --- | --- | --- |
| 安裝／重建 | 主機 CPU、記憶體、磁碟 I/O | 短時間較高；本機 webpack 抽樣 RSS 合計峰值約 2.27 GiB |
| 日常主機執行 | 既有面板服務、品牌 JSON 讀取、靜態檔案傳輸 | 新增邏輯少；沒有新增常駐 Node.js 服務，未量測相對原版的執行時 CPU／RAM 百分比 |
| 訪客瀏覽器 | JavaScript、CPU／繪圖資源、貼圖與畫面緩衝 | 折射、模糊、透鏡、捲動與尺寸變動是主要來源 |
| 冷快取下載 | 主機對外流量與訪客下載時間 | 隨新用戶數成長；預設 Logo 是明顯的單一檔案成本 |

## 數據的範圍

以下區分檔案量測、本機建置抽樣與依程式碼推算。沒有進行目標 Linux 主機的負載壓測、原版／主題版的同條件 A/B 量測，或跨裝置 GPU／電池量測。因此不能據此宣稱主題固定增加某個 CPU 百分比、固定幀率，或固定數量的常駐記憶體。

本版公開更新是文件與發行整理，介面程式與先前已建置的整合版本一致。原始紀錄與量測工具不放進公開安裝包。

## 一、安裝建置：為什麼需要較多記憶體

同一份介面來源，在 Windows、Node.js v24.14.0 的一次 production webpack 建置中，直接監看 Node 程序及其子程序，結果如下：

| 指標 | 觀察值 |
| --- | --- |
| 建置結果 | 成功，結束碼 0 |
| 經過時間 | 約 29.69 秒 |
| 程序樹 RSS 合計的抽樣峰值 | 2323.46 MiB，約 2.27 GiB |
| 程序樹 private commit 合計的抽樣峰值 | 2520.51 MiB，約 2.46 GiB |
| 抽樣記錄到的 CPU 時間 | 約 52.78 CPU 秒 |
| 抽樣次數 | 43 次，名目等待間隔 500ms，另含查詢程序資訊的時間 |

這是 **Windows 的 webpack 建置參考**，不代表 Linux 上的固定值，也不涵蓋 yarn install、獨立 tsc、備份、PHP、作業系統或同機 Minecraft 的用量。RSS 合計可能重複計入共享頁面；private commit 不等於實體 RAM；抽樣可能錯過兩次讀取之間的峰值，CPU 時間也可能漏掉最後一小段。

約 53 CPU 秒分布在約 30 秒內，代表這次建置平均使用約 1.8 個核心等效的 CPU 時間，不能直接換算成你的主機 CPU 百分比。

Webpack 需要解析模組、建立相依圖、轉譯 TypeScript／JSX 與 CSS，並壓縮 JavaScript。上游 webpack 設定啟用了 Terser 平行壓縮，工作執行緒／程序與中間語法樹會增加記憶體需求。輸出只有幾 MB，不代表建置只需要幾 MB RAM。原版 Pterodactyl 的建置本來也需要這些工作；本次數據不是「主題獨自新增的 2.27 GiB」。

**容量建議：** 安裝器的「RAM＋swap 至少 2 GiB」只是最低檢查門檻，不保證足夠。依此次參考量測，建置時建議另外預留約 **3～4 GiB 可用記憶體餘裕**，再加上原本的 PHP、作業系統與遊戲負載。Swap 能緩解記憶體不足，但可能增加磁碟等待；同機有 Minecraft 時，建置競爭 CPU、RAM 或 I/O 仍可能影響遊戲。

## 二、日常主機：為什麼通常比建置輕

- 主題沒有新增長駐 Node.js、背景渲染器或替訪客運算玻璃畫面的服務；Node 主要用於建置與手動品牌設定。
- 品牌模板在產生 HTML／郵件時讀取 `public/branding/brand.json`。預設檔案是 **82 bytes**，但 PHP 檔案讀取與 JSON 物件的實際成本不是 82 bytes，也不是零；未量測每次請求的耗時或記憶體增量。
- 名稱、模式、動畫速度與霧面互動不會逐幀發送主機請求；速度設定保存在瀏覽器 localStorage。
- Dashboard 的資源資料仍沿用原版的每張適用伺服器卡片 **30 秒**輪詢。粗略平均請求率為「同時顯示卡片的總數 ÷ 30 秒」，例如 10 個用戶各看 3 張卡片約為 1 次／秒，另有初次載入的請求；這是既有面板負載，非玻璃動畫新增的輪詢。
- 同一部主機若同時執行面板與遊戲，靜態檔案流量、即時壓縮與原本 API 請求仍會共用 CPU、網路與記憶體。沒有目標主機量測時，不能承諾完全不影響遊戲。

比較官方來源與本版 `package.json`，`dependencies` 與 `devDependencies` 沒有新增或變更項目；既有依賴仍需被正確安裝。這不代表 node_modules 或套件快取不占磁碟。

## 三、磁碟與網路：實際檔案有多大

以下為對應整合版本的一份編譯產物快照，大小取近似值：

| 項目 | 大小 | 如何理解 |
| --- | --- | --- |
| 主 JavaScript bundle | 約 843 KiB；本機 gzip level 6 約 260 KiB | 包含面板本體與主題，不是主題單獨增加的大小 |
| manifest 中全部 16 個 JavaScript 檔案 | 約 2.64 MiB；各自 gzip level 6 合計約 758 KiB | 含延遲載入模組；不代表每個頁面首開都下載全部 |
| 一份預設 PNG Logo | 1,413,109 bytes，約 1.35 MiB | 通常載入 `panel-logo.png`；相同網址可重用瀏覽器快取 |
| 兩份預設 Logo 路徑 | 約 2.70 MiB 磁碟 | 保留相容性與品牌設定路徑，不代表正常頁面必定下載兩次 |
| 85 個目標來源檔案 | 合計約 3.01 MiB；相對乾淨來源淨增加約 2.80 MiB | 大部分新增位元組是 Logo；不含編譯資產、依賴、快取或備份 |

gzip 數字是本機計算，不是正式網站的實際 HTTP 傳輸量；主機是否啟用壓縮與快取、用戶造訪哪些頁面都會改變流量。假設冷快取用戶最終載入全部 JS，且主機以近似的 gzip 傳輸，再加一份原大小 Logo，合計約 **2.09 MiB**，還未包含 HTML、字型、API 與協定開銷；100 位這樣的用戶約 209 MiB。這是明確條件下的容量推算，不是每次登入的固定流量。

備份磁碟需求取決於原本的 `public/assets`、將被修改的來源、`yarn.lock` 及壓縮率。每次完整安裝、品牌更改都可能留下新備份；需另計保留數量，不能把 ZIP 大小當成完整安裝的磁碟需求。

## 四、瀏覽器：玻璃效果為什麼較重

### 貼圖產生與尺寸

`liquid-glass.js` 的 `buildMaps()` 會在主執行緒逐像素計算位移與高光，建立兩份 RGBA ImageData，再編碼成 PNG data URL。SVG filter 接著組合模糊、位移與高光；瀏覽器可能使用 GPU、CPU 或兩者，不能假設全部運算都免費交給顯示卡。

程式將 DPR 限制到 2、貼圖長邊限制到 2400px。若玻璃 CSS 尺寸為 `w × h`：

```text
k = min(devicePixelRatio, 2, 2400 / max(w, h))
W = round(w × k), H = round(h × k)
兩份 ImageData 的像素資料 ≈ W × H × 4 bytes × 2
```

例如 1296×117px 的玻璃在 DPR 2 時，貼圖約為 2400×217；兩份像素資料約 **3.97 MiB**。這只計算兩個像素陣列，不含 canvas、編碼字串、解碼影像、SVG filter、DOM 或合成緩衝，不能當成整個分頁的記憶體用量。

同尺寸、同參數的卡片能共用濾鏡貼圖，減少重複建立；每張卡片實際繪製與合成仍有成本。一般濾鏡在不再使用時會釋放引用；內容／透鏡尺寸快取目前沒有明確的容量上限，長時間反覆改變尺寸可能累積更多快取，不能承諾記憶體永不成長。

### 什麼操作會增加負載

- 首次顯示、調整視窗、改變導覽列高度、載入字型或切換模式，可能重新計算貼圖。雙排 Bar 的高度動畫也可能觸發 ResizeObserver；這段有產生新尺寸貼圖的成本。
- 捲動時需要更新邊緣狀態與背景明暗判斷。背後的終端機、圖表或其他內容變動時，模糊與合成也可能需要更新。
- 透鏡移動使用 requestAnimationFrame 與位置、縮放更新；沒有每一幀重建完整背景貼圖，但仍有腳本與繪圖工作。
- 更多可見玻璃卡片、更大的面積、更多重疊圖層與高更新率螢幕，通常增加可執行的工作量；實際影響取決於裝置、瀏覽器與驅動。

程式以事件觸發並合併每幀更新，沒有一直運轉的透鏡動畫迴圈；終端機的高頻子節點變更也有跳過掃描。這些措施減少重複工作，但不保證所有裝置都能穩定達到某個 FPS。

### 調慢動畫不等於節能

速度拉桿改的是播放速率與彈簧模擬時間，不是畫面更新率。requestAnimationFrame 通常仍配合螢幕更新率排程；0.25× 可能使透鏡繼續運算更多幀，總耗電不一定較少。

例如程式的 2000ms 模擬時間界線，在 0.25× 且幀間隔正常時可拉長到約 8 秒；卡頓時還可能更長，且正常收斂時會提早結束。因此此拉桿用於觀看與偏好，不是低耗能模式。

### 玻璃貼圖在背景執行緒產生（1.2.0）

- 每片玻璃依尺寸需要兩張貼圖（折射方向、鏡面高光），要逐一計算每個像素。整條導覽列在 2 倍解析度螢幕上約 60 萬個像素；彩虹的薄膜色還要多算三角函數。
- 1.2.0 以前這些計算在主執行緒進行：換頁出現新尺寸的玻璃、改視窗大小、切換彩虹時，頁面會被卡住。量測（無 GPU 的無頭 Chromium、2 倍解析度、同一測試頁）主執行緒最長一次被佔用：打開彩虹 **334ms**、新頁面的玻璃出現 **311ms**、改視窗大小 **227ms**。
- 1.2.0 改由 Web Worker 計算並壓縮成 PNG，以上三種情況主執行緒被佔用都是 **0ms**；貼圖好了才換上，期間保留目前的樣子。瀏覽器不允許 Worker 時退回主執行緒計算，畫面完全相同。
- 彩虹的薄膜色先在 2 CSS px 的格點上計算再雙線性內插，與逐點計算的差異小於一個色階（截圖比對最大差 4/255），計算量少了十幾倍。

### 一定要開啟瀏覽器的硬體加速

玻璃的折射（SVG 位移濾鏡＋模糊）在 GPU 上很便宜，用 CPU 畫則非常慢：在沒有 GPU 的測試瀏覽器裡，一片導覽列玻璃每次重畫就要數十毫秒，捲動或動畫時每幀可能 50–170ms。如果面板在某台電腦特別卡，先確認：

- Chrome／Edge：設定 → 系統 →「可用時使用圖形加速」要開啟，改完重新啟動瀏覽器
- 網址列輸入 `chrome://gpu`（Edge 為 `edge://gpu`），Graphics Feature Status 裡的 Canvas、Compositing、Rasterization 應為 Hardware accelerated
- 遠端桌面、部分虛擬機、驅動過舊時，瀏覽器可能自動改用軟體繪圖

### 彩虹世界（淺色模式）的成本

- **導覽列的稜鏡色散**：導覽列的折射濾鏡改成紅、綠、藍三個通道各做一次位移再合成，位移運算約為原本的三倍。只有導覽列使用；其他玻璃只在高光圖裡加上薄膜干涉色（每種尺寸算一次，之後每幀成本不變）。量測（無 GPU、CPU 軟體繪圖、捲動 2.5 秒）：淺色一般主題每幀中位數約 33ms，淺色彩虹約 50ms，差距幾乎都來自色散。這是最壞情況的相對比較，不代表有 GPU 的瀏覽器的實際幀數。
- **桌布、珍珠色卡片、光譜色的光**：都是靜態的 CSS 漸層，畫一次之後沒有每幀成本，沒有新增 backdrop-filter。
- **沒有一直在播放的動畫**：進入時的開場（光點、泡泡、彩虹、稜鏡光、果凍波、星光、圖示重組，約 2.7 秒）、按下時的小泡泡都只在被觸發時播放，播完就移除 canvas。開場期間畫面上的玻璃每幀重畫，成本和捲動相同，只發生在切換的那一下。原因：瀏覽器在有東西持續變動時要重畫畫面，只要變動的地方靠近玻璃（或瀏覽器整個畫面重畫），玻璃的折射每一幀都得重算。開發時試過「寬螢幕兩側一直飄的泡泡」與「流動的載入條」，在測試頁上讓滑鼠移動時的幀數從約 117 掉到約 25–36，所以都沒有採用。
- **所有人看到的都一樣**：沒有依裝置效能降級的模式；動畫以實際時間計算，慢的裝置只是少畫幾幀，速度、路徑、長度都相同；所有新效果都用 CSS／canvas 畫，不下載圖片。動畫的亂數用固定種子，每個人每次看到的是同一場動畫。

### 點陣圖示與邊緣光

- **點陣圖示**（深淺色開關、設定開關、控制台霧化按鈕）是 13 × 13 格的小 canvas。只有切換的那一下會播放約 0.7 秒（跟著全域動畫速度）的像素重組動畫，平時是靜止的畫面，不佔任何每幀成本；切換深淺色時會在顏色轉場期間重畫幾幀，讓顏色跟上。
- **邊緣光**是 CSS 漸層與遮罩，程式只在游標移動時（合併成每幀最多一次）寫入角度與位置。導覽列的開關追整個頁面的游標；設定開關只在游標在開關附近時才追，頁面上開關很多也不會每次移動都全部重算。
- **玻璃邊緣的細光**沿用玻璃原本就在追蹤的游標位置，沒有新增監聽。
- 系統「減少動態效果」時：圖示直接換、邊緣光不追游標、停在固定角度。

### Logo 的解碼成本

預設 Logo 為 1254×1254。若完整解碼成一份 RGBA 緩衝，算式 `1254 × 1254 × 4` 約為 **6.00 MiB**，即使導覽列只顯示小圖。瀏覽器可能縮小解碼、共用影像或保留多份副本，所以這不是實際占用的保證。

自訂 Logo 可優先選擇合適的 256×256 或 512×512 PNG。256×256 的單份 RGBA 像素資料僅 0.25 MiB；實際下載大小仍依圖片內容與壓縮而異。

## 建議與評估界線

1. 建置時把既有面板、遊戲與系統負載一起計算，預留記憶體與磁碟，不把 2 GiB 門檻當安全保證。
2. 優先使用較小、清楚的 Logo；依既有維運方式檢查靜態檔案快取／壓縮。本文件不會自動更改 nginx。
3. 低階裝置可使用作業系統「減少動態效果」；目前會抑制部分動態與透鏡，但不是完全關閉所有毛玻璃的省資源開關。
4. 避免一次顯示過多大型玻璃區塊；若仍有卡頓，應以實際裝置檢查主執行緒與繪圖時間，再決定是否調整效果。
5. 沒有同條件原版對照與 Linux RSS／CPU 量測前，不宣稱固定的增量百分比、固定可承載人數，或固定的瀏覽器 RAM／GPU 用量。
